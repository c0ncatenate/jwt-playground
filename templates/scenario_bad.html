Scenario 4 – Bad practices (training only)

This scenario is here to show what not to do with JWTs. Everything on this page is intentionally unsafe and exists purely for defensive security training.

1. Weak secret key

Using an easily guessed or leaked secret key means attackers can mint their own admin tokens. The code in this lab uses a deliberately bad key: 

INSECURE_SECRET = "do-not-use-this-in-production"

Issue a token with this weak secret and imagine what happens if that line ends up in logs, screenshots, or a public repo.

2. Accepting alg=none / skipping verification

Some historical vulnerabilities came from servers trusting tokens with alg = none or skipping signature verification entirely. This effectively turns a JWT into an editable JSON blob.
